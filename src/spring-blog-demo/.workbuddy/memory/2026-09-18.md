# 2026-09-18 工作日志

## 排查「拦截器是否被调用」（用户疑问）

**结论：拦截器有被调用，注册正确，用户观察到的现象是「成功放行时无日志」导致误判。**

证据链：
1. `SpringBlogDemoApplication` 在 `com.example.springblogdemo` 包下 → `config` / `common.interceptor` 均在扫描范围。
2. `WebConfig` 构造器注入 `LoginInterceptor` 成功 = Bean 存在；若注册失败会在启动时直接报错，不会静默失效。
3. 历史日志出现过 `WARN ... LoginInterceptor : 请求被拦截：未携带 token，uri=/blog/deleteBlog`，该行只可能由 `preHandle` 打出。

**误判原因**：`preHandle` 原来 4 条出口中，3 条失败分支有 `log.warn`，唯一的「校验通过」路径完全静默 → 登录后正常操作在控制台看不到拦截器痕迹。
**次要原因**：`addPathPatterns` 只列 4 个写接口，用 Postman 测读接口（`getList`/`getBlogDetail`/`countByUser`/`getAuthorInfo`）时拦截器确实不执行，属设计如此。

### 改动 1：`LoginInterceptor` 增加放行日志
在 `request.setAttribute(...)` 之后、`return true` 之前加：
```java
log.info("登录校验通过，userId:{}, uri:{}, method:{}",
        userId, request.getRequestURI(), request.getMethod());
```
目的：让拦截器的存在对观察者可见，避免再次误判。

### 改动 2：新增观测拦截器 `LogInterceptor`
- 路径：`common/interceptor/LogInterceptor.java`
- 拦 `/**` 全部路径，`preHandle` 永远 `return true`，**不做任何鉴权**。
- 存在意义：`LoginInterceptor` 只挂 4 个写接口，无法证明「全局拦截机制在工作」；本类连静态资源都打日志，可直接证明 Spring MVC 拦截器链路通畅。
- `WebConfig` 中先注册它、再注册 `LoginInterceptor`（先注册先执行）。
- **明确标注**：它不是安全措施，别因为它拦 `/**` 就以为全接口受保护；排查完建议注释掉，否则静态资源刷屏。

### 改动 3：`BlogException` 重构（此前盘点两轮的 P0 项）
原实现问题：`@Data` + 自定义 `private String message`，构造器只 `this.message = message`，**未调 `super(message)`** → 业务提示能正常返回（Lombok getter 覆盖了），但 `Throwable.detailMessage` 恒为 null，**打堆栈时显示 `BlogException: null`**，排查困难。
改法：
```java
public class BlogException extends RuntimeException {
    public BlogException(String message) {
        super(message);   // 交给父类保存
    }
}
```
同时删除 `code` 字段 + 双参构造器 —— 已 Grep 全项目确认无任何调用方（全项目 12 处 `new BlogException("...")` 均为单参），零影响。
